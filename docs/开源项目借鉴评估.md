# 开源项目借鉴评估（2026-11-23）

> 硬件基线：MT8167S 四核 A35 @1.5GHz / 1GB RAM / Android 8.1 / armv7。
> 证据分层：**已验证** = 本项目实测；**有据** = 项目官方 README 或明确实测报告；
> **待验证** = 需要在本设备实测才能确认；**不适用** = 硬件或许可硬约束下排除。

## 结论先行

最值得借鉴的不是"换一个更炫的模型"，而是两件事：

1. **silero-vad 替掉现在的能量阈值判停**——这是当前 A 方案（0.45s 固定静音）的根源，
   换成神经 VAD 后可以既更快又不误切句中停顿。MIT 许可、2MB、<1ms/帧。
2. **sherpa-onnx 流式 Zipformer 替换 Vosk**——有 armv7 真机实测数据支撑，
   识别质量提升空间很大（我们现在回环测试把"名字"听成"女性"）。

其余项目要么只支持英语（openWakeWord）、要么是给 MCU 的（microWakeWord）、
要么是云端方案（端到端语音），对这台设备价值有限。

## 三个值得动手的方向（按投入产出排序）

### 方向 1：silero-vad 替换能量阈值判停

**现在的问题**：`record()` 每 0.12s 看一次 ch0 峰值，>700 算人声，静音超过 0.45s 判停。
这是纯能量判据，无法区分"句中停顿"和"说完了"，所以 A 方案只能保守取 0.45。

**换成 VAD 后**：模型输出每帧的语音概率，能识别停顿中的轻声、呼吸，
判停可以基于连续 N 帧无语音而不是固定静音时长，理论上能压到 0.3s 以内且不误切。

**落地步骤**：
1. 先确认设备上 `onnxruntime` 是否有 armv7 + Python 3.14 的 wheel
2. 没有的话，用 C++ 版或自行交叉编译（风险点）
3. 用现有 20 句录音做 A/B：对比误切率和判停耗时
4. 只有指标全面优于 0.45s 才替换

**成本**：中。**风险**：中（依赖 armv7 的 ONNX Runtime 可用性）。

### 方向 2：sherpa-onnx 流式 Zipformer 替换 Vosk

**现在的问题**：Vosk small-cn 识别质量一般，回环测试把"名字"听成"女性"。
虽然真人语音条件更好，但错字会传给 DeepSeek，直接影响回答质量。

**可行依据**：有 armv7 真机实测——Cortex-A7@1.2GHz/512MB 跑 14M INT8 流式 Zipformer，
RTF 0.85、延迟 210ms、内存 98MB。我们的 A35@1.5GHz/1GB 配置更高。
另一份 A53 实测 CER 3.77%（Vosk small 中文官方 CER 约 15–20% 量级）。

**关键坑（来自实测报告）**：
- 不能全 INT8：`decoder` 必须保持 FP32，否则出现重复循环输出（"漂亮漂亮亮主妇妇"），
  CER 从 3.87% 暴涨到 25.34%
- 正确组合：`encoder-int8 + decoder-fp32 + joiner-int8`
- 线程不是越多越快：低端 ARM 瓶颈是内存带宽，推荐 threads=3、chunkMs=100~150

**落地步骤**：
1. 下载 `sherpa-onnx-v2.0.1-android.tar.bz2`，取 `armeabi-v7a` 的 .so
2. 下载 14M 流式 zipformer 模型（bilingual）
3. 先在设备上跑 CER/RTF 评测脚本，确认优于 Vosk 再替换
4. 保留 Vosk 作为降级路径

**成本**：高（要接 native 库）。**风险**：中（模型体积、内存、SAC 未签名 .so 拦截——
本机开启了 Smart App Control，未签名 .so 会被拦，这是硬约束，需要先验证）。

### 方向 3：查 AEC 参考通道，为全双工打断做准备

WebRTC AEC3 需要两路音频：麦克风采集流 + 播放给扬声器的参考流。
如果系统能拿到参考流，就能做真正的打断（说话时不用等播完）。
如果拿不到，只能用"识别播放文本做回声抑制"的软件近似方案。

**成本**：低（只做调研）。**风险**：低。

---

## 不建议做

- **换唤醒模型**：openWakeWord 只有英语，microWakeWord 要重训且是给 MCU 的。
  现有 Vosk 限定词表在 20% 音量下回环稳定唤醒，没有必要折腾。
- **本地神经 TTS**：ZipVoice 123MB + A35 上 RTF 很可能 >1，比现在的云端 Edge TTS 慢，
  还会挤占 Vosk 的内存。明确排除。
- **端到端语音**：牺牲本地 ASR 和断网可用这个核心优势，换一个依赖公网的方案，方向不对。
- **Wyoming 协议**：现有 `/api/events` 已经是事件驱动，换协议收益有限、改动面大。

## 落地验证记录（2026-11-23 下午）

### 方向 3：AEC 参考通道 —— 调研完成

设备音频子系统：

- `tinymix` 93 个控件，有 `AP_Loopback_Select`（硬件环回，不等于播放参考流）
- `/system/etc/audio_effects.conf` 里 aec / agc / ns **全部被注释掉**，
  且写着 "TODO: add default audio pre processor configurations after debug and tuning phase"
  —— 说明这台设备没有启用 Android 原生 AEC
- `audio_policy_configuration.xml` 有 `voice_tx` / `voice_rx` 通道，但没有现成的参考流导出

**结论**：系统级 AEC 不可用。但有一条应用层路径——我们自己控制 TTS 播放，
知道播了什么 mp3，可以作为 AEC3 的 `ProcessReverseStream` 参考输入。
需要把 WebRTC AEC3 交叉编译到 armv7 + JNI，工程量中高。
**优先级低，暂不做**（现有"播报时压唤醒"已解决主要问题，全双工打断是锦上添花）。

### 方向 1：silero-vad —— 硬前提不成立，另试替代方案也失败

**神经 VAD 走不通**：

- 设备是 `armv7l` + Python 3.14.10
- PyPI 上 onnxruntime 最新版 1.32.0：**ARM32 wheel 数量为 0**；
  cp314 只有 aarch64 / x86_64 / macOS，没有 armv7
- 现有 `libvosk.so` 导出符号里没有 VAD / silero 相关符号

**替代方案（双阈值判停）也验证失败**：

不用神经网络，改成"高阈值 700 重置高计数、低阈值 280 只重置低计数，两个都静音才停"。
用 5 段带停顿录音回放对比：

```
单阈值 0.45   切点准确，不误切
双阈值 0.30/0.45  早切 1.56~4.20s   ← 全部失败
```

原因：这些录音峰值是二元的（要么 >700、要么 <280），没有"轻声过渡区"，
低阈值完全不起作用，反而让 0.30s 的高阈值提前触发。

**结论**：方向 1 不改，保留 b1120-71 的 0.45s 判据。
两个方案都试过了，数据不支持更激进的改动。

### 方向 2：sherpa-onnx —— 进行中

发现官方有专门的 `sherpa-onnx-v2.0.1-android-armeabi-v7a-termux-shared.tar.bz2`
（16MB，正是 Termux 用的 armv7 共享库包），比通用的 45MB Android 包合适得多。
设备下载中。评测脚本 `asr/test_sherpa.py` 已备好。

需要澄清一点：之前评估写的"SAC 会拦未签名 .so"是**错的**——
SAC 是 Windows 主机的策略，只管 PC 上加载的 DLL；Android 设备上的 .so 是 Linux ELF，
不受其管辖。现有 `libvosk.so` 已经能正常加载就是证明。
真正的风险是 Android SELinux / Termux 的加载限制，这个用实测验证。


### 方向 2：sherpa-onnx —— 运行时可用，但整体不部署

**已验证**：

- 官方有专门的 `sherpa-onnx-v2.0.1-android-armeabi-v7a-termux-shared.tar.bz2`（16MB）
- 设备在 setsid 后台、逐片校验下载后成功解压
- `sherpa-onnx-version` 正常运行，输出：
  ```
  sherpa-onnx version : 2.0.1
  onnxruntime version : 1.28.2
  ```
  → **armv7 + Termux 能加载 ONNX Runtime 1.28.2**，之前担心的原生库加载问题不成立。

**放弃的原因**：

1. **模型包 511MB**：`sherpa-onnx-streaming-zipformer-bilingual-zh-en-2023-02-20.tar.bz2`
   实际大小 511,274,346 字节（不只是 14M 模型，整包含多版本/精度）。
   设备下载速度约 20KB/s，要下 5 小时以上。HuggingFace 单文件下载在本网络不通。
2. **VAD 工具链不完整**：`sherpa-onnx-vad` 启动报
   `cannot locate symbol _ZNSt6__ndk113__hash_memoryEPKvj` —— 这是 Android NDK libc++
   特有的符号，Termux 的 libc++ 没有。补 `LD_LIBRARY_PATH` 指向 Termux libc++ 仍失败。
   即：version 工具能跑，但涉及实际推理的工具链缺符号，需要重新编译或换静态包（148MB）。

**结论**：运行时可行性已证实，但模型获取和工具链成本超出本轮范围。
保留 `asr/test_sherpa.py` 等验证工具在仓库，日后若拿到模型可直接复测。
当前 ASR 维持 Vosk。

## 本轮最终状态

三个方向全部实测过，结论：

| 方向 | 结果 |
|---|---|
| AEC 参考通道 | 调研完成：系统 AEC 未启用；应用层自参考可行但需 native 编译，优先级低 |
| silero-vad 神经 VAD | 硬前提不成立（无 ARM32 wheel）；双阈值替代方案回放验证失败 |
| sherpa-onnx ASR | 运行时可用已证实；模型 511MB + VAD 工具链缺符号，不部署 |

**设备代码未改动，仍是 b1120-71。** 多轮回归 25/25 通过，唤醒全链路正常，
无错误日志，看门狗健康。所有验证工具与结论已入仓库。

这轮的价值在于**排除了三条看起来很美但在这台设备上走不通的路**，
并把"armv7 能跑 ONNX Runtime 1.28.2"这个此前不确定的前提变成了已验证事实。
