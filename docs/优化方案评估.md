# 大肥鱼音箱 · 进一步优化方案评估

> 状态：D、A 已部署（b1120-71，2026-11-23）；其余仍为评估。硬件基线：MT8167S 四核 A35 @1.5GHz / 1GB RAM / Android 8.1。
> 所有收益数字来自本机实测或硬件规格推算，不是厂家宣传口径。

## 现状与瓶颈

当前实测（b1120-70）：

| 环节 | 耗时 |
|---|---|
| 语音唤醒 | ~0.4s |
| 本地 ASR（Vosk） | ~0.8–1.2s |
| DeepSeek 流式首句 | 0.63–1.11s |
| TTS 首句（连接复用） | 0.47–1.59s |
| **用户说完 → 首声** | **约 0.66s（API 触发口径）/ 2–3s（含 ASR 全链路）** |

已经做到：流式逐句开播、TTS 连接复用、固定话术预合成、LRU 缓存、电脑兜底。
剩下能压的，主要不在"TTS 引擎"本身，而在 ASR 尾点判断和唤醒 Detection 这两段。

---

## 方案清单（按性价比排序）

### A. 流式 ASR 尾点提前（✅ 已部署，取保守值 0.45s）

**做什么**：Vosk 现在是"检测到静音 0.62s 才判定说完"。改成在识别到完整词序列、
能量掉到阈值以下时就提前收尾，把 0.62s 的静音等待压到 0.25–0.3s。

**收益**：用户说完到开播**再省 0.3–0.4s**。
**成本**：中。只改 `record()` 的 `silence` 参数和尾点判据，不动架构。
**风险**：中。压太狠会把句中停顿当成说完（"那个…我想说"会被切断）。
需要保留一个"秒级补全"机制：切断后若 0.5s 内又有人声，把两次识别拼起来。
**结果**：回放验证 0.35 会误切 500ms 停顿，最终取 0.45（安全，省 0.17s）。

### B. 端到端语音对话（E2E，颠覆性但硬件不支持）

**做什么**：跳过 ASR→LLM→TTS 三段，直接音频进音频出（如 GPT-4o voice / 阿里 Qwen-Omni）。

**收益**：理论上首响压到 0.3s 以内，且保留语气、情绪。
**成本**：极高。豆包/端侧小模型在 1GB A35 上跑不动，只能走云端大模型。
**风险**：高。云端 E2E 依赖公网稳定性，断网直接哑；延迟受网络抖动支配，
在弱网下反而比现在的本地 ASR 更慢。
**结论**：**不推荐**。这台设备的价值恰恰是本地 ASR + 弱网可用，换成 E2E 等于自废武功。

### C. 本地神经 TTS（sherpa-onnx + ZipVoice / Piper）

**做什么**：小米开源 ZipVoice 123M 参数、支持中文、有 ONNX INT8 + sherpa-onnx CPU 部署。

**收益**：完全离线合成，断网也能说话。
**成本**：极高。INT8 模型 123MB；sherpa-onnx 主要面向 arm64，本机 armv7 需自编；
A35 1.5GHz 上 RTF 很可能 >1（合成 3 秒音频要 3 秒以上），比现在的云端方案还慢。
**风险**：高。1GB RAM 里塞 123MB 模型 + Vosk 模型 + 系统，内存吃紧；
自编原生库还要过 SAC 签名关。
**结论**：**不推荐**。这是上一轮就排除过的路线，硬件物理不支持。

### D. 唤醒后预连接（✅ 已部署，无声预热；预播"我在"方案已否决）

**做什么**：唤醒词命中的瞬间（确认是"肥鱼肥鱼"）就提前：
1. 复用池里那条 WebSocket 提前 warm 一次；
2. 对"我在""请讲"这类 100% 会用的确认语先播缓存。

**收益**：省 0.2–0.4s 的冷启动感；用户能立刻听到"我在"反馈，主观体感提升明显。
**成本**：低。复用池已具备，只需在 wake 事件里加一次预热调用。
**风险**：低。预播"我在"会稍微增加总输出时长，但 perceptual latency 明显下降。
**结果**：已做无声预热版本；"我在"预播被否决，理由见上。

### E. 播报期间全双工打断（barge-in）

**做什么**：现在播报时靠 `/api/wake {active:false}` 压住唤醒，用户插话要等播完才响应。
改成播放时降低唤醒门限，检测到人声就立刻停音频并转入听。

**收益**：体验提升大，像真人对话。
**成本**：中高。要处理回声（音箱自己的声音被麦克风听到），
本机 4 麦阵列理论上可做 AEC，但驱动层是否暴露参考信号未知。
**风险**：高。误打断（把电视声当人声）会显著恶化体验，需要专门的判据。
**建议**：**先做调研**，确认能不能拿到播放音频的参考通道，拿不到就不做。

### F. 电脑侧备选增强：预热与连接池

**做什么**：PC 的 `tts_server.py` 加长连接复用和固定话术预合成（设备端已有，PC 端只加了缓存）。

**收益**：设备切到电脑兜底时，延迟和设备直连一致。
**成本**：低。edge-tts 官方库本身支持 stream，复用要改调用方式。
**风险**：低。电脑兜底是低频路径。
**建议**：可做，优先级低于 A、D。

### G. 缓存策略升级：语义缓存

**做什么**：现在按"音色|音调|语速|精确文本"做 key。改成对相似问法归一
（"几点了" / "现在几点" / "几点" 命中同一缓存）。

**收益**：对高频问法有奇效，但 DeepSeek 每次回答措辞不同，实际命中率可能很低。
**成本**：中。需要文本归一化规则或小模型做意图聚类。
**风险**：中。归一错误会导致答非所问。
**结论**：**不推荐**。当前 DeepSeek 回答是生成式的，同问题不同措辞，语义缓存意义不大。

---

## 推荐组合

1. **先做 D**（唤醒瞬间预热 + "我在"预播）—— 低风险、体感提升明显
2. **再做 A**（流式 ASR 尾点提前）—— 需先用录音回放验证误切率
3. **调研 E 的硬件前提**（AEC 参考通道），拿不到就放弃
4. 其余（B/C/G）**明确不做**

需要你选定再实施。**本轮没有部署任何方案。**
